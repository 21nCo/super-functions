---
title: Administration and operator service
description: Bind scoped HostFn deployment operations to a host-owned control plane.
---

The HostFn CLI deploys an application from a developer or CI machine. The separate `hostfn/operator` entry point and `@hostfn/admin` package let a host application expose deployment administration through Super Console. The capability is a contract; it does not provision a control plane by itself.

## What the host supplies

`HostFnOperatorService` takes a `HostFnOperatorStore` and a `HostFnDeploymentExecutor`. The store owns targets, deployments, domains, and variable metadata. `putVariable(variable, secretValue)` also receives the plaintext secret before the executor runs, and the memory store may retain it. Production stores must protect retained values at rest, restrict access, and avoid logging them—or deliberately avoid persisting the value while preserving the metadata required by the store contract. The executor performs external deploy, cancel, rollback, restart, domain, and variable effects. `MemoryHostFnOperatorStore` is a reference store for development and single-process installations; use a durable implementation for a production control plane.

Every operator record carries an `installationId`, `workspaceId`, `projectId`, and `environmentId` scope. The host must derive the active scope from the authenticated admin context and enforce authorization before invoking the adapter. Domain attachment uses an immutable identity and a reclaimable work lease so retries do not attach the same hostname to a different target. The external executor must be idempotent for retries with the same domain ID.

## Capability resources and actions

| Resource | Reads | Actions |
| --- | --- | --- |
| Targets | List and get | Restart |
| Deployments | List and get | Deploy, cancel, rollback |
| Domains | List | Attach, detach |
| Variables | List keys | Set, delete |

Variable values are never returned by the list operation. Target server addresses are marked sensitive in the capability. Read and write operations have separate permissions. Destructive actions, including variable deletion, require MFA confirmation; variable setting requires recent authentication; deploy and domain attach require explicit confirmation for their external effects. These are declared confirmation requirements: the host must supply a confirmation service whose verifier validates the requested method and `maxAgeSeconds` freshness. The dispatcher only checks the verifier’s boolean decision; a permissive verifier does not enforce MFA or recent authentication. All writes require audit evidence through the shared admin dispatcher.

## Binding the adapter

Create an operator service with your store and executor, then pass it to `createHostFnOperatorAdminService` and `createHostFnAdminAdapter` from `@hostfn/admin`. The host must connect the adapter to its authenticated Super Console dispatcher and supply the active environment scope. The [operator source](https://github.com/21nCo/super-functions/blob/dev/hostfn/cli/src/operator.ts) and [admin capability](https://github.com/21nCo/super-functions/blob/dev/hostfn/admin/src/index.ts) define the exact interfaces and operation IDs.

Use the complete [SuperConsoleOptions and service interfaces](https://github.com/21nCo/super-functions/blob/dev/superconsole/src/lib/server/types.ts) for the binding: register the adapter in `adapters`, include `hostfn` in `enabledModules`, and implement the operator-auth provider's `authenticate` and `authorizeScope` methods as well as the mutation hook below. Keep the bundled console's default `/api/admin/v1` base path. Supply `openApiSecuritySchemes` with both `operatorSession` and `operatorApiKey` describing your authentication provider.

Every HostFn write is declared idempotent. Supply a durable store implementing the complete [AdminIdempotencyStore interface](https://github.com/21nCo/super-functions/blob/dev/packages/admin/src/idempotency.ts): `begin`, `complete`, `release`, `finalizeAudit`, `prepareCompensation`, `claimCompensation`, and `releaseCompensation`. The initial Super Console presence check inspects only the first three methods; the dispatcher constructor also requires the terminal-audit reconciliation and compensation hooks, even before an operation uses them. Implement their atomic, claim-fenced transitions and retry semantics as specified in the interface; no-op hooks do not satisfy the production contract.

Pass an idempotency key with each write request. A standalone dispatcher returns `dependency_unavailable` without a store and `precondition_failed` without a key; `createSuperConsole` rejects a missing store at startup. The operator store's domain lease protects one domain workflow but does not replace dispatcher idempotency across all mutations.

Supply a durable [AdminAuditSink](https://github.com/21nCo/super-functions/blob/dev/packages/admin/src/audit.ts) with `write` and `idempotentById: true`. The dispatcher rejects a sink without this capability marker at construction. Writes must be durable and first-write-wins by event ID, including retries after a lost acknowledgement; setting the marker alone does not provide those guarantees. Configure this sink alongside the confirmation service and authorization policies before exposing operations.

When binding through `createSuperConsole`, the operator-auth provider must implement `auth.authorizeMutation({ principal, request })`. Startup rejects the configuration without this hook because HostFn exposes mutations. The hook must reject unauthorized mutation requests; an `AdminPolicyEvaluator` does not replace this operator-auth check. Supply `shellPolicy.authorize` for console-surface access as well as the dispatcher's operation policy for scope and permission checks. These are separate authorization boundaries, not interchangeable services.

Also provide a `SuperConsoleConfirmationService`, not only a verifier. It must implement `issue`, `prepareActivation`, `cancelActivation`, `activate`, `revoke`, and `verify`; Super Console checks these methods at startup because HostFn mutations require confirmation. A token remains unusable while staged, and activation follows durable audit preparation. The service must keep cancellation and revocation effective so a denied or abandoned token cannot later authorize a write.

This integration is distinct from the CLI deployment flow. Review [deployment locks](/docs/documentation/advanced/deployment-locks), [rollbacks](/docs/documentation/advanced/rollback), and [environment variables](/docs/documentation/environment/overview) as background on the CLI implementation. The operator service delegates these effects to `HostFnDeploymentExecutor`; it does not inherit the CLI’s remote lock files, backup-based rollback, or `.env` layout. The host must implement any corresponding concurrency, recovery, and secret-handling guarantees in its executor and control plane.
