Plugins implement named callbacks on `DatafnPlugin`; there is no event subscription array. `runsOn` selects the client, server, or both. Register the object with `plugins: [plugin]` when creating the client or server.

## Hook context and arguments

```typescript
import type { DatafnHookContext, DatafnPlugin } from "@datafn/core";

export const auditPlugin: DatafnPlugin = {
  name: "audit-mutations",
  runsOn: ["server"],
  beforeMutation(ctx, mutation) {
    console.log("before mutation", ctx.env, mutation);
    return mutation;
  },
  afterMutation(ctx, mutation, result) {
    console.log("after mutation", ctx.env, mutation, result);
    // This callback observes the result; its return value is ignored by the caller.
  },
};
```

`DatafnHookContext` contains `env: "client" | "server"`, `schema: DatafnSchema`, and optional host `context`. It does not contain an event name, resource filter, or payload. The operation payload is a separate argument. Treat `context` and payloads as unknown until narrowed by application code.

| Callback | Arguments after `ctx` | Purpose |
| --- | --- | --- |
| `beforeQuery` | query | Inspect or replace the query. |
| `afterQuery` | query, result | Inspect the result; only server-side `afterQuery` can replace the result returned to the caller. |
| `beforeSearch` | search | Server only: inspect or replace the search request. Client search does not invoke this hook. |
| `beforeMutation` | mutation or mutation array | Inspect or replace the mutation payload. |
| `afterMutation` | mutation or mutation array, result | Observe the completed operation; return values do not replace the caller’s result. |
| `beforeSync` | phase, payload | Inspect or replace the sync payload. |
| `afterSync` | phase, payload, result | Observe a sync operation; return values do not replace the caller’s result. |

Sync phases are `seed`, `clone`, `pull`, `push`, `cloneUp`, and `reconcile`. There are no `beforeTransact` or `afterTransact` members in the current plugin contract.

## Ordering, return values, and failures

Hooks execute in registration order for plugins whose `runsOn` includes the current environment. For before-hooks, an undefined return keeps the current payload and a defined return supplies the next hook’s input. Only server-side `afterQuery` propagates its final replacement result to the operation caller. Client `afterQuery`, `afterMutation`, and `afterSync` return the original operation result; server `afterMutation` and `afterSync` also discard the hook runner’s final value. A replacement may reach subsequent hooks but does not replace these callers’ results. Preserve the shape expected by the operation. Returning `{ abort: ... }` is not an abort protocol: it would replace the payload.

Before-hooks fail closed: throwing stops the chain and fails the operation. After-hooks fail open: errors are logged and subsequent hooks continue. After-hooks cannot roll back an operation that has already executed. Keep authorization in the server's authorization policy; a client plugin is not a security boundary.

## Restricting a hook to a resource

Inspect the payload explicitly; the plugin contract has no `filter` property. Handle arrays when processing mutations:

```typescript
import type { DatafnPlugin } from "@datafn/core";

export const observeItems: DatafnPlugin = {
  name: "observe-items",
  runsOn: ["client", "server"],
  beforeMutation(_ctx, payload) {
    for (const mutation of Array.isArray(payload) ? payload : [payload]) {
      if (typeof mutation !== "object" || mutation === null) continue;
      if ("resource" in mutation && mutation.resource === "items") {
        console.log("items mutation", mutation);
      }
    }
    return payload;
  },
};
```

For reliable external side effects, persist an outbox record with the application's transaction and deliver it separately. An after-hook alone does not provide durable delivery or rollback.
