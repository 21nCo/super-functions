# OpenAPI

Every authfn server can emit an **OpenAPI 3.1 document** that describes exactly the routes your enabled plugin set exposes. The document is generated from the same plugin descriptors that build the router, so it is always in sync with the running surface.

## Enabling generation

Pass `openApi` at construction:

```ts
const auth = createAuthFn({
  // ...
  openApi: {
    title: 'AuthFn API',
    version: '1.0.0',
  },
});
```

You can also pass `true` for default title/version, or `false` (or omit) to disable generation entirely. When disabled, `auth.openApi` is undefined.

## Reading the document

Call `auth.openApi()` whenever you need it. The document is computed lazily and is safe to call repeatedly.

```ts
const document = auth.openApi();
```

## Serving the document

Mount it on whatever path you like:

### Hono

```ts
app.get('/openapi.json', (c) => c.json(auth.openApi?.() ?? {}));
```

### Express

```ts
app.get('/openapi.json', (_req, res) => res.json(auth.openApi?.() ?? {}));
```

### SvelteKit

```ts
// src/routes/openapi.json/+server.ts
export const GET = () => json(auth.openApi?.() ?? {});
```

### Next.js Route Handler

```ts
export async function GET() {
  return Response.json(auth.openApi?.() ?? {});
}
```

## What's in it

The document includes:

- **Paths and operations** for every route registered by an enabled plugin.
- **Tags** — every operation is tagged with `authfn` (and a plugin-specific tag where applicable).
- **Operation IDs** — stable, in `camelCase` (`signUpWithPassword`, `verifyEmailOtp`, …).
- **Summaries** — one-line descriptions per operation.
- **Components** — request/response schemas where defined; will be expanded as plugins migrate to declared schemas.

Disabling a plugin removes its operations from the document automatically.

## What it's missing today

The current document is intentionally small at the schema level. Operation IDs, paths, and tags are present and stable; full request/response component schemas are landed for the highest-traffic operations and being expanded over time.

If you want richer schemas, we recommend either:

- **Run authfn behind a typed wrapper.** The first-party SDKs (`@authfn/client`, the Python package, `AuthFnSwift`) already encode the schemas. Use them directly.
- **Generate from the SDK types.** The TypeScript types in `@authfn/core` are the source of truth; `tsc --emitDeclarationOnly` plus a small adapter gives you a typed wire schema.

## Build-time generation

This documentation site generates an OpenAPI snapshot at build time so the [API reference](../api) page always reflects the canonical full surface. The snapshot is generated by `scripts/generate-openapi.mjs` (in the docs site) and committed as `content/api/authfn.json`.

If you publish your own authfn deployment as a separate document, follow the same pattern — generate the JSON from your *deployed* plugin set, then render it with your favorite OpenAPI viewer.

## Validating clients

If you generate API clients from OpenAPI (e.g. with `openapi-typescript`, `kiota`, or `oapi-codegen`), point them at the generated `authfn.json`. The first-party SDKs do not depend on the document; they follow the same wire contract directly. The two sources are diff-tested in CI to keep them in sync.

## Custom routes

If you author your own plugin and want it documented in the generated OpenAPI, declare your route's `summary`, `operationId`, and `tags` in the route descriptor. The plugin runner picks them up automatically.

```ts
routes: () => [
  {
    method: 'POST',
    path: '/my-plugin/widget',
    operationId: 'createWidget',
    summary: 'Create a new widget',
    tags: ['authfn', 'my-plugin'],
    handler: async () => /* ... */,
  },
]
```

## Versioning

OpenAPI's `info.version` is whatever you supply. The wire contract itself follows semver: a new endpoint or new optional field is a minor version; a deletion or a required-field rename is a major version. Track the contract version separately from the runtime version.
