## What

`sendfn` is a self-deployable, unified communications platform SDK that provides email and push notification capabilities with persistence, event tracking, and suppression list management. The v0 implementation focuses on AWS SES for email, FCM/APNS for push notifications, and a database-agnostic architecture using the Superfunctions adapter pattern.

### Core Capabilities

- **Email Sending & Receiving** - Transactional emails via AWS SES
- **Template Management** - In-codebase templates with variable interpolation
- **Push Notifications** - Multi-platform support (FCM for Android, APNS for iOS)
- **Suppression Lists** - Automatic bounce, complaint, and unsubscribe management
- **Event Tracking** - Delivery, bounce, complaint, open, click events via AWS SES
- **Database Integration** - Adapter-based persistence for transactions, device tokens, and suppressions
- **Provider Abstraction** - Interface-based design allowing future providers (SendGrid, Mailgun, etc.)

## Why

**Problem:**

- Building communication systems requires integrating multiple providers (SES, FCM, APNS)
- Managing email suppressions, bounces, and complaints is complex
- Tracking email events across providers lacks standardization
- Push notification token management requires custom infrastructure
- No unified SDK for email + push in the Superfunctions ecosystem

**Value:**

- **Unified API** - Single SDK for all communication channels
- **Provider Agnostic** - Swap email/push providers without code changes
- **Production Ready** - Built-in suppression lists, event tracking, retry logic
- **Self-Deployable** - No external SaaS dependencies beyond cloud providers
- **Database Flexible** - Works with any ORM via adapter pattern
- **Type Safe** - Full TypeScript support with Zod validation

## Notes

### Design Decisions

**1. Provider Abstraction**

- Use interface-based design for email and push providers
- Allows adding new providers (SendGrid, Mailgun, OneSignal) without changing core logic
- Each provider implements standardized interface with capabilities declaration

**2. Database Adapter Pattern**

- Follow `@superfunctions/db` adapter pattern for consistency
- Consumers can use any ORM (Drizzle, Prisma, Kysely)
- Provides memory adapter for testing without database

**3. Suppression List Strategy**

- Automatic suppression on permanent bounces and complaints
- Configurable thresholds for transient bounces
- Manual suppression for user unsubscribes
- Soft-delete (keep records for compliance)

**4. Event Tracking Architecture**

- All events stored in single table with polymorphic reference
- Supports email and push events
- Webhook handlers update transactions and record events atomically
- Queryable by type, date range, user, etc.

**5. Template Engine Choice**

- Lightweight custom engine (no dependencies)
- Simple syntax: `{{variable}}`, `{{#if}}`, `{{#each}}`
- HTML escaping by default for security
- Future: Consider Handlebars or Mustache for advanced features

**6. Push Notification Strategy**

- Separate providers for FCM and APNS (platform-specific)
- Automatic token invalidation on failed sends
- Device tokens stored per user + platform
- Support for multi-device users

### Trade-offs

**Database Adapter vs. Direct ORM**

- ✅ Flexibility: Works with any ORM
- ✅ Testing: Memory adapter for tests
- ❌ Complexity: Requires adapter implementation
- **Decision:** Use adapter for flexibility

**Custom Template Engine vs. Handlebars**

- ✅ No dependencies, lightweight
- ✅ Sufficient for v0 use cases
- ❌ Less powerful than Handlebars
- **Decision:** Custom for v0, revisit in v1

**Webhook vs. Polling for Events**

- ✅ Real-time event processing with webhooks
- ✅ More reliable than polling
- ❌ Requires HTTPS endpoint setup
- **Decision:** Webhook-based (standard for SES/SNS)

**Single SDK vs. Separate Packages**

- ✅ Unified API, simpler for consumers
- ❌ Larger bundle size if only using email
- **Decision:** Single SDK, tree-shakeable exports

## Parity Goals

### TypeScript vs. Python

The goal is 100% feature parity between TypeScript and Python SDKs.

- **Models:** Zod schemas (TS) <=> Pydantic models (Python)
- **Interfaces:** TypeScript Interfaces <=> Python Protocols
- **Async:** Both SDKs must be fully async/await compatible
- **DX:** Both SDKs must provide idiomatic experiences (e.g., TypedDict for params in Python)
